# 6.1 Configuration

*Last Updated: 2026-05-27*

> The TOML file `setup` writes, every field's meaning, what's overridable at runtime.

Configuration is **per-profile**. Each profile owns its own directory and its own `config.toml`:

- `prod` → `~/.proxai/proxai-gateway/prod/config.toml`
- `dev` → `~/.proxai/proxai-gateway/dev/config.toml`
- Windows: `%LOCALAPPDATA%\proxai\proxai-gateway\<profile>\config.toml`

`buildProfileContext('prod' | 'dev')` (`src/core/io/fs/profile.ts`) is the single constructor for every per-profile path and the default Nest base URL. The `setup` command writes the file for the targeted profile; the daemon (`run --profile <name>`) reads it once at start and uses the in-memory `GatewayConfig` for the lifetime of the process. TOML was chosen via `smol-toml` — a small TOML parser — because it's human-editable, has typed sections, and the parser ships as one tiny dependency.

The file is written atomically and chmod'd to `0o600`, alongside the rest of that profile's state (the profile's own [buffer](../03-buffer/3.1-buffer.md) `buffer.db`, its [sentinels](../04-daemon-loops/4.4-sentinels.md), and its log directory). The two profiles share nothing: each has an independent `config.toml`, `buffer.db`, log dir, and sentinel set. See [6.5 Dev Mode & Profiles](./6.5-dev-mode-and-profiles.md) for how the profiles relate to the dev-mode CLI toggle.

## The five tables

Five top-level tables, each with a single purpose:

| table | purpose |
| --- | --- |
| **`[account]`** | identity — `api_key`, `user_id`, `host_id`, `installed_at`, `install_source`. All five required; the daemon refuses to start without them |
| **`[backend]`** | the four endpoint URLs from the [backend protocol](../05-backend/5.1-backend-protocol.md). Defaulted from the profile's `defaultNestBaseUrl` (prod → Railway, dev → `localhost:3001`) |
| **`[capture]`** | the operational tuning surface — retention windows, soft-pause hysteresis, pacer budgets, 429 backoff multiplier, max decompressed limit |
| **`[logging]`** | pino log level and on-disk log directory |
| **`[stale_binary]`** | warn/pause-after-days thresholds for the [heartbeat cycle](../04-daemon-loops/4.3-heartbeat-cycle.md)'s stale-binary policy |

## How defaults work

The default values are not in the TOML file — they live in `services/config/config.constants.ts` and are filled in by `validateAndCoerce` whenever a field is missing from the loaded config. That means an operator can write a minimal TOML with just the required `[account]` fields and the daemon will run on defaults for everything else.

Validation runs on every load: numbers are coerced from strings, ranges are checked, and out-of-spec values are rejected with explicit error messages. The most important cross-field check is `buffer_soft_resume_bytes < buffer_soft_pause_bytes` — a degenerate hysteresis loop is rejected at load time.

## Runtime overrides

There is no live config reload — the daemon snapshots `config.toml` at start and never re-reads it. The two override paths are:

- **Profile selection.** The `--profile <prod|dev>` flag picks which directory's `config.toml` is loaded and which `defaultNestBaseUrl` is used. This is the only way the resolved Nest base URL changes: `dev` resolves to `http://localhost:3001`, `prod` to the Railway production URL. There is no environment variable that overrides the endpoint — `buildProfileContext` hard-codes the two base URLs and `setup` writes the four derived URLs verbatim into `[backend]`. To point an install at a different Nest, edit `[backend]` directly and restart, or re-run `setup --force`.
- **CLI flag `--config <path>`.** The daemon entrypoints (`run`, the god-mode `xstate`) accept `--config <path>` and forward it to `loadConfigFromFile`, useful for testing an alternative config without overwriting the canonical one. Commands that only read state default to the targeted profile's `configFilePath`.

## What's not exposed

The daemon-loop intervals (`CAPTURE_INTERVAL_MS = 120_000`, `DRAIN_INTERVAL_MS = 30_000`, `HEARTBEAT_INTERVAL_MS = 3_600_000`) are deliberately **not** exposed via `config.toml` — they are hard-coded in `polling.constants.ts` and only overridable via the per-loop `options` argument to `runDaemonLoops` (used by tests).

The `[capture] poll_interval_sec` field is validated and written by `setup` (default 300, range 60..3600) but has no effect on the three-loop daemon, which uses the hard-coded interval constants. It is a legacy single-loop knob kept for backward compatibility. Field-by-field meanings of every TOML key are documented in the FAQs below.

## Where does the config file live?

`buildProfileContext(profile).configFilePath` returns, per profile:

- macOS / Linux: `~/.proxai/proxai-gateway/<profile>/config.toml`
- Windows: `%LOCALAPPDATA%\proxai\proxai-gateway\<profile>\config.toml`

where `<profile>` is `prod` or `dev`. `writeConfigToFile` writes atomically and `setMode(filePath, 0o600)`s it (owner-only). `loadConfigFromFile(path?)` parses via `smol-toml` and runs `validateAndCoerce`, which fills defaults from `config.constants.ts` for missing fields and rejects out-of-range values.

## What does the TOML structure look like?

Five top-level tables. Field names on disk are `snake_case`; the in-memory `GatewayConfig` type uses `camelCase`. Defaults below come from `config.constants.ts`.

```toml
[account]
api_key       = "<ingestion key>"          # required
user_id       = "<userId from verify-key>" # required
host_id       = "<sha256 of machine:user>" # required
installed_at  = "<ISO-8601 UTC>"           # required
install_source = "github_release"          # one of bun|pnpm|yarn|npm|brew|github_release

[backend]
# All optional; default to the profile's base URL (prod = Railway, dev = http://localhost:3001)
ingest_url           = "<baseUrl>/v1/raw_records"
verify_key_url       = "<baseUrl>/ingestion/verify-key"
watermarks_url       = "<baseUrl>/v1/watermarks"
register_host_id_url = "<baseUrl>/v1/host-ids/register"

[capture]
poll_interval_sec              = 300       # 60..3600; legacy, unused by the three-loop daemon
buffer_path                    = "<~/.proxai/proxai-gateway/<profile>/buffer.db>"
receipt_retention_days         = 365       # >= 0
failed_retention_days          = 365       # >= 0
buffer_soft_pause_bytes        = 53687091200 # 50 GiB, > 0, > soft_resume
buffer_soft_resume_bytes       = 48318382080 # 45 GiB, >= 0, < soft_pause
upload_max_batches_per_sec     = 5         # >= 0.1
upload_max_bytes_per_minute    = 52428800   # 50 MiB, > 0
upload_backoff_on_429_multiplier = 2        # >= 1
# max_decompressed_bytes       = 9437184    # optional; > 0 or +Infinity

[logging]
level   = "info"            # one of fatal|error|warn|info|debug|trace; default "info"
log_dir = "<platform default>"

[stale_binary]
warn_after_days  = 30   # >= 0; 0 disables warn
pause_after_days = 60   # >= 0; 0 disables pause
```

Validation enforces `buffer_soft_resume_bytes < buffer_soft_pause_bytes` (otherwise the hysteresis loop is degenerate) and rejects strings where numbers are expected.

## What does each section do?

- **`[account]`** — identity. All five fields are required; `setup` writes them and the daemon refuses to start without them. `install_source` controls the auto-upgrade branch (brew uses the sentinel path, others replace the binary in place).
- **`[backend]`** — the four endpoint URLs. Defaulted from the profile's `defaultNestBaseUrl` (`buildProfileContext` returns the Railway production URL for `prod` and `http://localhost:3001` for `dev`), expanded by the `nest*Url` helpers. Overriding here lets an operator point at a different Nest without changing the binary.
- **`[capture]`** — the operational tuning knobs. The defaults come from `config.constants.ts`: **365-day** receipt and failed retention, 50/45 GiB hysteresis, 5 batches/sec (min 0.1), 50 MiB/min, 2x backoff on 429, and a default poll interval of 300 s (range 60..3600, currently unused by the daemon).
- **`[logging]`** — log level and on-disk directory. `validate.ts` checks the level against `VALID_LOG_LEVELS` and `expandHome`s the log dir. The default is `info`: `setup` writes it via `build-config.ts`, and `DEFAULT_LOG_LEVEL` resolves to the same value so a config-less code path produces the same result.
- **`[stale_binary]`** — the warn/pause-after-days thresholds for the stale-binary check. See [sentinels](../04-daemon-loops/4.4-sentinels.md) for the policy semantics.

## What's overridable at runtime?

There is no environment variable that overrides the Nest base URL — the two base URLs are hard-coded in `buildProfileContext` and selected purely by `--profile`. The only config-related env vars are the maintainer-only `PROXAI_GATEWAY_CAPTURE_SUB_AGENTS*` capture flags, read once at module load. The override surfaces are:

- **Profile (`--profile <prod|dev>`)**: selects the directory whose `config.toml` is loaded and the `defaultNestBaseUrl` baked into `[backend]` defaults. The daemon then constructs `HttpClient` from `deps.config.backend.*`, so the persisted TOML values are authoritative at runtime. To repoint a running install, edit `[backend]` and restart, or re-run `setup --force`.
- **CLI flag `--config <path>`**: the daemon entrypoints (`run`, the god-mode `xstate`) accept `--config` and forward it to `loadConfigFromFile`. State-reading commands default to the targeted profile's `configFilePath`.

The daemon-loop intervals (`CAPTURE_INTERVAL_MS = 120_000`, `DRAIN_INTERVAL_MS = 30_000`, `HEARTBEAT_INTERVAL_MS = 3_600_000`) are not exposed via `config.toml` — they are hard-coded in `polling.constants.ts` and only overridable via the per-loop `options` arg to `runDaemonLoops` (used by tests). The `[capture] poll_interval_sec` field is a legacy single-loop knob, retained for backward compatibility but unused by the three-loop daemon.

## How does `setup` decide what `install_source` to record?

The `setup` command takes `--install-source <source>` (defaults to `github_release` per `main.ts`). Allowed values are `bun`, `pnpm`, `yarn`, `npm`, `brew`, `github_release` (validated against `VALID_INSTALL_SOURCES`). The package-manager-specific install scripts (`postinstall` hooks for npm/pnpm/yarn/bun, brew formula, install.sh/install.ps1 for the curl-bash path) each invoke `setup` with the matching `--install-source`. Anything else fails the install-source parse with a clear validation error.

Once written, `install_source` drives:

- The `--version` "installed via …" line (read at startup by `buildVersionString`).
- The auto-upgrade branch in `runHeartbeatCycle.shouldRunAutoUpgrade`.
- The `uninstall` flow's package-manager sweep (`createSweep`).

## How does `max_decompressed_bytes` work?

Optional override of `BODY_TARGET_DECOMPRESSED_BYTES` (~9 MiB) for the slicer's "max raw bytes per slice" budget. `resolveMaxDecompressed(capture)` returns `capture.maxDecompressedBytes ?? BODY_TARGET_DECOMPRESSED_BYTES`. The validator accepts any positive finite number, plus `Number.POSITIVE_INFINITY` (used by tests to disable the split entirely). Lower values produce more, smaller batches; higher values produce fewer, larger batches up to the hard 10 MiB ceiling enforced inside the collectors.
