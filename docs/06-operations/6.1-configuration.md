# 6.1 Configuration

> The TOML file `setup` writes, every field's meaning, what's overridable at runtime.

Configuration lives in one TOML file at `~/.proxai/proxai-gateway/config.toml` (or `%LOCALAPPDATA%\proxai\proxai-gateway\config.toml` on Windows). The `setup` command writes it; the daemon reads it once at start and uses the in-memory `GatewayConfig` for the lifetime of the process. TOML was chosen via `smol-toml` — a small TOML parser; the config file is TOML — because it's human-editable, has typed sections, and the parser ships as one tiny dependency.

The file is written atomically and chmod'd to `0o600`, alongside the rest of the gateway's per-host state (the [buffer](../03-buffer/3.1-buffer.md), [sentinels](../04-daemon-loops/4.4-sentinels.md), and per-platform log directory).

## The five tables

Five top-level tables, each with a single purpose:

| table | purpose |
| --- | --- |
| **`[account]`** | identity — `api_key`, `user_id`, `host_id`, `installed_at`, `install_source`. All five required; the daemon refuses to start without them |
| **`[backend]`** | the four endpoint URLs from the [backend protocol](../05-backend/5.1-backend-protocol.md) |
| **`[capture]`** | the operational tuning surface — retention windows, soft-pause hysteresis, initial-scan window, pacer budgets, 429 backoff multiplier |
| **`[logging]`** | pino log level and on-disk log directory |
| **`[stale_binary]`** | warn/pause-after-days thresholds for the [heartbeat cycle](../04-daemon-loops/4.3-heartbeat-cycle.md)'s stale-binary policy |

## How defaults work

The default values are not in the TOML file — they live in `services/config/config.constants.ts` and are filled in by `validateAndCoerce` whenever a field is missing from the loaded config. That means an operator can write a minimal TOML with just the required `[account]` fields and the daemon will run on defaults for everything else.

Validation runs on every load: numbers are coerced from strings, ranges are checked, and out-of-spec values are rejected with explicit error messages. The most important cross-field check is `buffer_soft_resume_bytes < buffer_soft_pause_bytes` — a degenerate hysteresis loop is rejected at load time.

## Runtime overrides

Runtime overrides come in two flavors:

- **Environment variables.** `PROXAI_GATEWAY_NEST_ENDPOINT` overrides the resolved nest base URL at process start, before `setup` runs. Once `setup` writes the resolved URL into `[backend]`, the env var has no further effect on a running daemon; `setup --force` is what re-reads it.
- **CLI flag.** Every command that loads config (`run`, `dev`, `status`, `tail`, `inspect`, etc.) accepts `--config <path>` and forwards it to `loadConfigFromFile`, useful for testing alternative configs without overwriting the canonical one.

## What's not exposed

The daemon-loop intervals (`CAPTURE_INTERVAL_MS = 120_000`, `DRAIN_INTERVAL_MS = 30_000`, `HEARTBEAT_INTERVAL_MS = 3_600_000`) are deliberately **not** exposed via `config.toml` — they are hard-coded in `polling.constants.ts` and only overridable via the per-loop `options` argument to `runDaemonLoops` (used by tests).

The legacy `[capture] poll_interval_sec` field is retained for backward compatibility with older single-loop builds but has no effect on the three-loop daemon. Field-by-field meanings of every TOML key are documented in the FAQs below.

## Where does the config file live?

`configFilePath()` returns:

- macOS / Linux: `~/.proxai/proxai-gateway/config.toml`
- Windows: `%LOCALAPPDATA%\proxai\proxai-gateway\config.toml`

`writeConfigToFile` writes atomically and `setMode(filePath, 0o600)`s it (owner-only). `loadConfigFromFile(path?)` parses via `smol-toml` and runs `validateAndCoerce`, which fills defaults for missing fields and rejects out-of-range values.

## What does the TOML structure look like?

Five top-level tables. Field names on disk are `snake_case`; the in-memory `GatewayConfig` type uses `camelCase`. Defaults below come from `config.constants.ts`.

```toml
[account]
api_key       = "<ingestion key>"          # required
user_id       = "<userId from verify-key>" # required
host_id       = "<sha256 of machine:user>" # required
installed_at  = "<ISO-8601 UTC>"           # required
install_source = "github_release"          # one of bun|pnpm|yarn|npm|brew|github_release

[backend]
ingest_url           = "<NEST_INGEST_URL>"           # optional; defaults to NEST_INGEST_URL
verify_key_url       = "<NEST_VERIFY_KEY_URL>"       # optional
watermarks_url       = "<NEST_WATERMARKS_URL>"       # optional
register_host_id_url = "<NEST_REGISTER_HOST_ID_URL>" # optional

[capture]
poll_interval_sec              = 300       # 60..3600 (legacy unified loop control)
buffer_path                    = "<~/.proxai/proxai-gateway/buffer.db>"
receipt_retention_days         = 30        # >= 0
failed_retention_days          = 30        # >= 0
buffer_soft_pause_bytes        = 734003200  # 700 MiB, > 0, > soft_resume
buffer_soft_resume_bytes       = 629145600  # 600 MiB, >= 0, < soft_pause
initial_scan_window_days       = 30        # >= 0
upload_max_batches_per_sec     = 5         # > 0
upload_max_bytes_per_minute    = 52428800   # 50 MiB, > 0
upload_backoff_on_429_multiplier = 2        # >= 1
# max_decompressed_bytes       = 9437184    # optional; > 0 or +Infinity

[logging]
level   = "info"            # one of fatal|error|warn|info|debug|trace; default "trace"
log_dir = "<platform default>"

[stale_binary]
warn_after_days  = 30   # >= 0; 0 disables warn
pause_after_days = 60   # >= 0; 0 disables pause
```

Validation enforces `buffer_soft_resume_bytes < buffer_soft_pause_bytes` (otherwise the hysteresis loop is degenerate) and rejects strings where numbers are expected.

## What does each section do?

- **`[account]`** — identity. All five fields are required; `setup` writes them and the daemon refuses to start without them. `install_source` controls the auto-upgrade branch (brew uses the sentinel path, others replace the binary in place).
- **`[backend]`** — the four endpoint URLs. Defaulted from `NEST_*_URL` constants which derive from `resolveNestBaseUrl(env)`. Overriding here lets a dev point at a local nest without changing env vars on every invocation.
- **`[capture]`** — the operational tuning knobs. The defaults align with the constants doc'd elsewhere: 30-day retention, 700/600 MiB hysteresis, 30-day initial scan, 5 batches/sec, 50 MiB/min, 2x backoff on 429.
- **`[logging]`** — log level and on-disk directory. `validate.ts` checks the level against `VALID_LOG_LEVELS` and `expandHome`s the log dir. The default is `info`: `setup` writes it via `build-config.ts`, and `DEFAULT_LOG_LEVEL` resolves to the same value so a config-less code path produces the same result.
- **`[stale_binary]`** — the warn/pause-after-days thresholds for the stale-binary check. See [sentinels](../04-daemon-loops/4.4-sentinels.md) for the policy semantics.

## What's overridable at runtime?

Two layers of override:

- **Environment**: `PROXAI_GATEWAY_NEST_ENDPOINT` overrides the resolved nest base URL at process start. `resolveNestBaseUrl(env)` runs at module load and produces the `NEST_*_URL` constants. `setup` reads those constants and writes them verbatim into `[backend]` of `config.toml`. After that, the daemon (`run` / `dev`) constructs `HttpClient` from `deps.config.backend.*`, so the persisted toml values are authoritative at runtime — `PROXAI_GATEWAY_NEST_ENDPOINT` set after a successful `setup` has no effect until the next `setup --force` rewrites the toml. To point a running install at a different nest, edit `[backend]` directly or re-run setup with the env var.
- **CLI flag `--config <path>`**: every command that reads config (`run`, `dev`, `status`, `tail`, `inspect`, etc.) accepts `--config` and forwards it to `loadConfigFromFile`. Useful for testing alternative configs without overwriting the canonical one.

The daemon-loop intervals (`CAPTURE_INTERVAL_MS`, `DRAIN_INTERVAL_MS`, `HEARTBEAT_INTERVAL_MS`) are not exposed via `config.toml` — they are hard-coded in `polling.constants.ts` and only overridable via the per-loop `options` arg to `runDaemonLoops` (used by tests). The `[capture] poll_interval_sec` field is a legacy single-loop knob, retained for backward compatibility but currently unused by the three-loop daemon.

## How does `setup` decide what `install_source` to record?

The `setup` command takes `--install-source <source>` (defaults to `github_release` per `main.ts`). Allowed values are `bun`, `pnpm`, `yarn`, `npm`, `brew`, `github_release` (validated against `VALID_INSTALL_SOURCES`). The package-manager-specific install scripts (`postinstall` hooks for npm/pnpm/yarn/bun, brew formula, install.sh/install.ps1 for the curl-bash path) each invoke `setup` with the matching `--install-source`. Anything else fails the install-source parse with a clear validation error.

Once written, `install_source` drives:

- The `--version` "installed via …" line (read at startup by `buildVersionString`).
- The auto-upgrade branch in `runHeartbeatCycle.shouldRunAutoUpgrade`.
- The `uninstall` flow's package-manager sweep (`createSweep`).

## How does `max_decompressed_bytes` work?

Optional override of `BODY_TARGET_DECOMPRESSED_BYTES` (~9 MiB) for the slicer's "max raw bytes per slice" budget. `resolveMaxDecompressed(capture)` returns `capture.maxDecompressedBytes ?? BODY_TARGET_DECOMPRESSED_BYTES`. The validator accepts any positive finite number, plus `Number.POSITIVE_INFINITY` (used by tests to disable the split entirely). Lower values produce more, smaller batches; higher values produce fewer, larger batches up to the hard 10 MiB ceiling enforced inside the collectors.
