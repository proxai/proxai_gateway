# 2.1 Sources

*Last Updated: 2026-05-27*

> Which agents the gateway watches, where their on-disk session files live, and how each one is shaped.

A source is one supported coding-agent CLI plus the on-disk shape of the data it produces. The gateway watches four agents — `claude-code`, `cursor`, `codex`, `gemini-cli` — and treats each agent's session artifacts as a stream of additive bytes or rows that can be sliced by a [watermark](./2.2-parsing-and-watermarks.md) (a per-file `[start, end)` interval that says "everything below `end` has been captured").

Sources live in `src/sources/<app>/` and each implements the same poller scaffold: discover candidate files, filter by mtime (if a threshold is specified), then collect new bytes or rows per file and hand them off to the parse-filter-trim-redact-compress-insert pipeline. The gateway does not forward source files unchanged — every record in the new slice is parsed, a per-source filter keeps only genuine dialogue content, and a per-source trim strips oversized or non-dialogue fields from the records it keeps before redaction and compression.

## Two axes: sourceApp and sourceKind

The taxonomy has two axes: `sourceApp` (which agent wrote the file) and `sourceKind` (what shape it is on disk). Three `sourceKind` values cover all four agents:

- `jsonl_append` — newline-delimited append-only logs.
- `sqlite_kv_snapshot` — Cursor's `cursorDiskKV` key-value table.
- `sqlite_table_snapshot` — Codex's named state tables.

The combination of `(sourceApp, sourceKind)` is what the `SOURCE_VARIANTS` table in `services/contract/contract.constants.ts` enumerates. There are five entries because Codex appears twice (once for jsonl rollouts, once for its sqlite state file).

## Why each agent looks different

Each agent flushes data differently, so the gateway has per-source handling:

- **Claude Code** writes one jsonl per project under `~/.claude/projects/`.
- **Codex** nests jsonl rollouts in timestamp directories plus a numbered sqlite state file.
- **Cursor** writes a single sqlite database (plus per-workspace siblings) that the gateway snapshots via Bun's sqlite snapshot to avoid blocking the agent's writer.
- **Gemini CLI** puts a header line at the top of each chat that the gateway must skip before reading event records.

Each variant maps deterministically to a body format (`jsonl`, `kv_pairs_json`, `sqlite_rows_json`) and a watermark kind (`byte_range` or `rowid_range`) — covered in [parsing and watermarks](./2.2-parsing-and-watermarks.md).

## Discovery: the mtime filter window

Discovery is optionally bounded against a `minimumMtime` (filesystem-recorded modification time) threshold so a fresh install does not back-fill the entire history of every agent's session files on first run. The capture loop can pass this cutoff via the `minimumMtimeOverride` context property (often used in test scenarios).

Once a file is in scope, the source emits one or more batches per [capture cycle](../04-daemon-loops/4.1-capture-cycle.md), each carrying its watermark slice into the [buffer](../03-buffer/3.1-buffer.md).

## Which agents are supported?

Four `source_app` values, declared in `services/contract/contract.constants.ts`: `claude-code`, `cursor`, `codex`, `gemini-cli`. There are five `SOURCE_VARIANTS` entries because `codex` exposes two kinds (jsonl rollouts and a sqlite state file). Each variant is the canonical tuple of `(sourceApp, sourceKind, bodyFormat, watermarkKind, watermarkTableRequired)`:

| sourceApp | sourceKind | bodyFormat | watermarkKind | table required? |
| --- | --- | --- | --- | --- |
| `claude-code` | `jsonl_append` | `jsonl` | `byte_range` | no |
| `codex` | `jsonl_append` | `jsonl` | `byte_range` | no |
| `cursor` | `sqlite_kv_snapshot` | `kv_pairs_json` | `rowid_range` | no |
| `codex` | `sqlite_table_snapshot` | `sqlite_rows_json` | `rowid_range` | **yes** |
| `gemini-cli` | `jsonl_append` | `jsonl` | `byte_range` | no |

The contract validator rejects any DTO whose `sourceApp` does not pair with the declared `sourceKind` / `bodyFormat` / `watermarkKind` combination.

## Where does each source's files live?

The base dir is always resolved from `$HOME` and joined with a per-source subpath, then walked with a Bun glob:

| source | base dir | glob (relative to base) |
| --- | --- | --- |
| `claude-code` | `~/.claude/projects` | `*/*.jsonl` |
| `cursor` | `~/Library/Application Support/Cursor/User` on macOS, `$HOME/.config/Cursor/User` on Linux, `%APPDATA%\Cursor\User` on Windows (`defaultCursorUserRoot(platform, env)` branches on `process.platform`; the three subpaths are `CURSOR_USER_SUBPATH`, `CURSOR_LINUX_USER_SUBPATH`, `CURSOR_WINDOWS_USER_SUBPATH` in `sources/cursor/cursor.constants.ts`) | `globalStorage/state.vscdb` and `workspaceStorage/*/state.vscdb` |
| `codex` (rollouts) | `~/.codex` | `sessions/*/*/*/rollout-*.jsonl` |
| `codex` (state) | `~/.codex` | `state_*.sqlite` (highest-numbered file wins) |
| `gemini-cli` | `~/.gemini/tmp` | `*/chats/**/*.jsonl` |

Discovery uses `Bun.Glob.scan({ onlyFiles: true })` and stats each match. Files older than the initial-scan window (see below) are filtered out before the source ever sees them.

## How does each source's body look on the wire?

Three formats, mapped 1:1 from the source kind. The body is never the raw on-disk slice — each format carries the parsed, filtered, and trimmed records:

- `jsonl_append` → `bodyFormat = jsonl`. The gateway reads the byte slice between the prior watermark and the current EOF, parses every line, drops lines the per-source filter rejects, and re-serializes the kept records (trimmed where the source defines a trim). The body is the newline-terminated join of the kept lines, after redaction. The watermark still advances to the physical EOF of the raw slice even when filtering removes lines.
- `sqlite_kv_snapshot` → `bodyFormat = kv_pairs_json`. The body is a JSON array of `{rowid, key, value}` rows from `cursorDiskKV` where `key` starts with `composerData:`, `bubbleId:`, or `agentKv:blob:`. Empty-text bubble rows and non-conversation `agentKv:blob:` rows are dropped, and each kept row's `value` is trimmed per prefix.
- `sqlite_table_snapshot` → `bodyFormat = sqlite_rows_json`. The body is a JSON array of `{rowid, …}` rows from one allowed Codex state table — the allow-list is `threads` and `thread_spawn_edges`.

All bodies are then zstd-compressed at level 3.

## How is the agent's own version reported?

Each source emits `agent_schema_version` on every batch:

- **claude-code** parses the jsonl looking for `version` or `message.version` on any line; falls back to the literal string `unknown`.
- **codex** rollouts call `extractRolloutCliVersion(sourcePath)`; falls back to the caller-provided default.
- **cursor** extracts the schema versions from `composerData:` and `bubbleId:` rows and formats them as `composerVersion:bubbleVersion` (falls back to `unknown:unknown`).
- **gemini-cli** spawns the resolved `gemini` binary with `--version`, validates against `/^[\w.+:/-]{1,64}$/`, and prefixes with `gemini-cli/`; falls back to `gemini-cli/unknown`.

If detection fails the gateway still ships the batch — only the schema-version field is degraded.

## What is the mtime filter window?

Each discover function takes a `minimumMtime` option and skips any file whose mtime is older than that timestamp. While the daemon's capture loop defaults to `null` (capturing all discovered files unconditionally), the testing harness and programmatic invocations can pass a dynamic `minimumMtimeOverride` (e.g. 30 days prior) to bound discovery scope.

## What happens when a file rotates or is deleted?

Discovery is mtime-bounded and stat-based: a renamed or deleted file simply stops appearing in the glob walk, and its cursor row stays behind. The cursor key includes the inode — the filesystem-level file identifier; tracking it lets the gateway notice when a path now points to a different underlying file (e.g., a log rotation) — in the `sourceInode` column (sentinel `0` when null), so when a new file appears at the same path with a different inode it gets a fresh cursor row with `watermarkEnd = 0` and is read from the start.

For sqlite sources the gateway can also detect a `VACUUM` — SQLite's `VACUUM` is a maintenance operation that rebuilds the database file to reclaim free pages and defragment storage; running it changes the database's page count, which is how the gateway detects it (size shrunk, page count dropped, or `max(rowid)+1 < cursor.watermark_end`). When `detectVacuum` returns true, the source path is suffixed with `#gen-N` and re-hashed, producing a new logical source identity so the old watermark is not reused against the rebuilt database.

## Per-source quirks worth knowing

- **claude-code** captures the parent-session glob `*/*.jsonl` by default. A second glob `*/*/subagents/*.jsonl` exists for sub-agent JSONL files but is gated behind the `PROXAI_GATEWAY_CAPTURE_SUB_AGENTS*` env-var flags (maintainer-only; see [6.4](../06-operations/6.4-maintainer-debug-flags.md)). When that flag is on, sub-agent lines carry an `agentId` field the receiver uses to compose `chat_id = sessionId:agentId`. Within a captured file the per-line filter keeps only genuine `user`/`assistant` dialogue text and drops tool-call/result records, `isMeta` records, synthetic command-wrapper records, and synthetic or error assistant records. Kept lines are shipped whole.
- **cursor** runs against a Bun snapshot of the live sqlite file (via `snapshotSqlite`), so the agent's writer is never blocked and the read sees a consistent state. Workspace databases are discovered alongside the global one; each is a separate source with its own cursor. The row filter allow-lists three key prefixes — `composerData:`, `bubbleId:`, and `agentKv:blob:` — and skips `composer.content.`, `checkpointId:`, `ofsContent:`, `inlineDiff:`, and `codeBlockPartialInlineDiffFates:` entirely. Kept row values are trimmed per prefix. `PROXAI_GATEWAY_CAPTURE_SUB_AGENTS_CURSOR` is accepted but does not change Cursor's row selection — the prefix set is fixed.
- **codex** keeps rollout jsonl files in nested timestamp directories and a numbered state file (`state_<N>.sqlite`). Only the highest-numbered state file is polled; older state files are ignored because Codex itself only writes to the highest. Rollouts use byte-range watermarks; state tables each get their own `rowid_range` watermark plus a `watermark_table` value — the allow-list is `threads` and `thread_spawn_edges`. The rollout filter keeps `session_meta`, turn-control `event_msg` records (`task_started`, `task_complete`, `turn_aborted`, `token_count`), and `response_item` message records (user/assistant); it drops the duplicate `event_msg` conversation channel, tool-call and tool-output `response_item` types, and `turn_context`. `session_meta` is trimmed (`base_instructions` and `dynamic_tools` stripped). By default the rollout discoverer pre-queries `thread_spawn_edges` and filters out child-thread rollouts; the maintainer flag disables that filter.
- **gemini-cli** chats start with a header line (the first newline-terminated record) that the gateway must skip. `GEMINI_CLI_HEADER_MAX_BYTES = 65536` (64 KiB) caps how far the header scan reads before giving up. When the cursor is fresh, the watermark advances past the header before any event slices are emitted. The record filter keeps `gemini` records and text-bearing `user` records, dropping `thought`, `tool_call`, `info`, and similar non-dialogue records; each kept `gemini` record is trimmed — tool-call `result`/`resultDisplay` dropped, oversized args capped, and `thoughts` reduced to subject and timestamp. The sub-agent flag is wired but no-op — Gemini's `invoke_agent` does not persist intermediate turns to disk.
