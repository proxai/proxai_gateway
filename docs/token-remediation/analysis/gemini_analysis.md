# Gemini (Antigravity CLI) Token Telemetry Audit Report

This report presents a comprehensive, consolidated telemetry audit of the **Gemini (Antigravity CLI)** parser family, as recorded in the raw database files. It evaluates prompt caching efficiency, explains the subtraction model and stateless output token summation implemented in [gemini.utils.ts](file:///Users/onurseckinsenoglu/repos/proxai/proxai_nest/src/agent-gateway/parsers/gemini/gemini.utils.ts#L395-L438), analyzes the efficiency benefits of Google context caching, and details the database vacuum/rotation detection and backend de-duplication systems.

### 1.1 Key Terminology & Baseline Formulae

*   **Interaction (Turn):** A complete execution cycle starting from a user prompt in the CLI, through all intermediate agent tool calls and executions, until the final text response is returned.
*   **Standard Input Tokens ($I_{std}$):** Volatile or newly processed prompt tokens that follow the last cache breakpoint, or the non-cached portion in Gemini.
*   **Cache Creation Tokens ($I_{create}$):** Newly processed tokens written to the cache for the first time.
*   **Cache Read Tokens ($I_{read}$):** Context tokens read directly from the prompt cache (cache hits).
*   **Output Tokens ($O_{std}$):** Tokens generated by the model (completions, tool call structures).
*   **True Billed Input ($I_{billed\_true}$):** The total input tokens that incur standard or premium charges:
    $$I_{billed\_true} = I_{std} + I_{create}$$
*   **True Processed Input ($I_{processed\_true}$):** The total context size evaluated by the model:
    $$I_{processed\_true} = I_{std} + I_{create} + I_{read}$$

## 🧮 2. Cache Hit Efficiency & Caching Leverage

We evaluate Gemini's prompt caching performance using two distinct definitions:

### Definition 1: Base Input excluding Cache Creation
This method measures the proportion of cached read tokens directly against the total processed prompt input (billed non-cached + cached reads):

$$\text{Cache Hit Efficiency}_1 = \frac{I_{read}}{I_{std} + I_{read}}$$

$$\text{Cache Hit Efficiency}_1 = \frac{7,557,104,839}{398,306,104 + 7,557,104,839} = \frac{7,557,104,839}{7,955,410,943} \approx \mathbf{94.99\%}$$

### Definition 2: Base Input including Cache Creation
This factors in the cache creation tokens, representing the total input tokens submitted to the Gemini API endpoint:

$$\text{Cache Hit Efficiency}_2 = \frac{I_{read}}{I_{std} + I_{read} + I_{create}}$$

$$\text{Cache Hit Efficiency}_2 = \frac{7,557,104,839}{398,306,104 + 7,557,104,839 + 13,713,776} = \frac{7,557,104,839}{7,969,124,719} \approx \mathbf{94.83\%}$$

### Caching Longevity and Amplification Ratios
1.  **Cache Reuse (Leverage) Factor:** The ratio of cache read tokens to cache creation tokens determines how many times a cached block is hit before invalidation:
    $$\text{Reuse Factor} = \frac{I_{read}}{I_{create}} = \frac{7,557,104,839}{13,713,776} \approx \mathbf{551.06\text{x}}$$
    On average, every token written to the cache is read **551.06 times**.
2.  **Input Context Multiplication Ratio:** The ratio of cached input tokens to billed non-cached input tokens indicates the factor by which context is amplified:
    $$\text{Multiplication Ratio} = \frac{I_{read}}{I_{std}} = \frac{7,557,104,839}{398,306,104} \approx \mathbf{18.97\text{x}}$$
    For every 1 billed input token sent to the API, Gemini reads 18.97 tokens from the cache.

## 🛠️ 3. NestJS Backend Core Parser Analysis

### 3.1 The Subtraction Model in `gemini.utils.ts`
Google Gemini's API reports total prompt size (`input_tokens`) as the sum of cached and non-cached inputs. If ProxAI recorded telemetry using raw `input_tokens` as billed input, it would double-bill cache-read tokens. To isolate actual newly-processed (billed) input tokens, `aggregateUsage` in [gemini.utils.ts](file:///Users/onurseckinsenoglu/repos/proxai/proxai_nest/src/agent-gateway/parsers/gemini/gemini.utils.ts#L395-L438) applies a **subtraction model**:

$$I_{billed} = I_{std} - I_{read}$$

```typescript
const nonCachedInput = (step.input_tokens ?? 0) - (step.cache_read_input_tokens ?? 0);
input += Math.max(0, nonCachedInput);
```

#### Impact of the Model:
Without this subtraction logic, recorded billed input would be **7,955,410,943 tokens** instead of **398,306,104 tokens**. Failing to apply the subtraction model would over-report standard billed input tokens by **7,557,104,839 tokens (a 1,997% / 20x overestimation)**.

### 3.2 Turn-Based Output Token Summation
Because the Gemini API is stateless, each step in a multi-step turn (e.g., executing a command or editing a file) sends the entire chat history back as a fresh request, producing new output tokens (whether tool-call definitions, thinking narration, or the final user markdown).

Output tokens do not accumulate. To determine the true output token consumption of a single turn, the system must sum output tokens across all steps:

$$\text{Turn Output Tokens} = \sum_{s \in \text{steps}} \text{step.output\_tokens}_s$$

```typescript
output += step.output_tokens ?? 0;
```

#### Impact of Summation:
If the parser only captured the output tokens of the final step (Step Type 23, Final assistant reply) and ignored the intermediate execution steps (Step Type 15):
*   Total Final Step Output ($O_{final}$): **457,251 tokens**
*   Total Intermediate Steps Output ($O_{intermediate}$): **34,167,149 tokens**
*   **Telemetry Loss % if not summed:**
    $$\text{Output Loss \%} = \frac{34,167,149}{34,624,400} = \mathbf{98.68\%}$$

By only recording the final step output, **98.68% of output token consumption would be lost**, leading to a severe under-billing of completion costs. Summing across all steps is an absolute engineering requirement for stateless agents.

## 🧮 5. Caching Token Efficiency Analysis

Gemini context caching offers a discount multiplier on cache reads (hits). On AI Studio, cache reads are discounted by 75% (0.25x equivalent billed input). On Vertex AI, cache reads are discounted by 90% (0.10x equivalent billed input).

### 5.1 AI Studio Scenario (75% discount multiplier)
*   **Without Caching:** $7,955,410,943$ standard input tokens are billed.
*   **With Caching:**
    *   Standard Input (Non-cached): $398,306,104$ tokens
    *   Cache Writes (Create): $13,713,776$ tokens
    *   Equivalent Cache Reads: $7,557,104,839 \times 0.25 = 1,889,276,209$ tokens
    *   *Total Equivalent Input*: $398,306,104 + 13,713,776 + 1,889,276,209 = \mathbf{2,301,296,089\text{ tokens}}$
*   **Equivalent Token Reduction:** **71.07%** reduction in total billed input context footprint.

### 5.2 Vertex AI Scenario (90% discount multiplier)
*   **Without Caching:** $7,955,410,943$ standard input tokens.
*   **With Caching:**
    *   Standard Input (Non-cached): $398,306,104$ tokens
    *   Cache Writes (Create): $13,713,776$ tokens
    *   Equivalent Cache Reads: $7,557,104,839 \times 0.10 = 755,710,483$ tokens
    *   *Total Equivalent Input*: $398,306,104 + 13,713,776 + 755,710,483 = \mathbf{1,167,730,363\text{ tokens}}$

## 🛡️ 6. Database Vacuum & Rotation Detection Pipeline

SQLite databases created by local AI agents undergo file modifications, truncations, or `VACUUM` events. If the gateway relied solely on a static file path or sequential `rowid` watermark, it would suffer from under-ingestion/data loss (when rowids regress) or duplicate ingestion. The gateway resolves this using a two-tier verification process:

```
[Local SQLite DB Path]
        │
        ▼
[resolveGeminiIdentity] ──► Query last cursor (size, page count, watermarkEnd)
        │
        ▼
[detectVacuum] ───────────► Check if size/pages decreased or rowid regressed
        │
        ├──► YES (vacuumed) ──► Increment suffix `#gen=N` ──► Reset watermark to -1 ──► Full Re-ingestion
        │
        └──► NO  (normal)   ──► Query rowid > prior cursor.watermarkEnd - 1
```

### 6.1 Tier 1: Gateway Identity Resolution (`resolve-identity.ts`)
1.  Query the local buffer database for the last recorded cursor mapping the file's path hash: `cursor = getCursorWithFallback(..., file.sourcePathHash)`.
2.  Extract `cursorSizeBytes`, `cursorPageCount`, and `cursorWatermarkEnd`.
3.  Measure the current snapshot state: `currentSizeBytes`, `currentPageCount`, and `currentMaxRowid`.
4.  Call `detectVacuum` in `src/services/buffer/vacuum-detect.ts`:
    ```typescript
    export function detectVacuum(s: VacuumSignals): VacuumDetectionResult {
      if (s.cursorSizeBytes !== null && s.currentSizeBytes < s.cursorSizeBytes) {
        return { vacuumed: true, reason: 'size_decreased' };
      }
      if (s.cursorPageCount !== null && s.currentPageCount < s.cursorPageCount) {
        return { vacuumed: true, reason: 'page_count_decreased' };
      }
      if (s.currentMaxRowid + 1 < s.cursorWatermarkEnd) {
        return { vacuumed: true, reason: 'rowid_regressed' };
      }
      return { vacuumed: false, reason: null };
    }
    ```
5.  If `vacuumed: true`, generate a new generation path suffix: `/path/to/gemini.db` becomes `/path/to/gemini.db#gen=1`. The hash is re-computed, and `rotated` is set to `true`.
6.  In `process-rows.ts`, if `rotated` is `true`, `priorCursor` is forced to `null` and `lastMaxRowid` defaults to `-1`, triggering a full re-ingestion of all rows.

### 6.2 Tier 2: NestJS Backend De-duplication Strategy
Re-ingesting the database from `rowid > -1` after a vacuum causes the gateway to re-upload previously parsed chat logs. To prevent duplicate records and double-billing, the NestJS backend employs a deterministic idempotency key:
1.  **Deterministic Record ID:** During turn finalization (`gemini-finalize-turn.service.ts`), the backend derives a deterministic record ID from `(agent, chatId, turnId)`:
    ```typescript
    const id = deterministicRecordId('gemini', chat.chatId, turnId);
    ```
    This function utilizes `blake2b512` and takes the first 32 characters of the resulting digest.
2.  **Consistent Upsert:** Ingestion is performed via Prisma `upsert`:
    ```prisma
    db.geminiCallRecord.upsert({
      where: { id: id },
      update: { ...parsedTelemetryData },
      create: { id: id, ...parsedTelemetryData }
    })
    ```
    This ensures that duplicate step uploads overwrite the existing row, maintaining a single, mathematically precise record per turn.

## 🛠️ 8. Actionable Recommendations & Integration Plan

To display accurate context scales and support the telemetry pipeline, we implement the following updates:

### Recommendation 1: Update UI Context Size Reporting
Because the ProxAI UI displays `result.usage.input_tokens` as "Input Tokens", it only shows the standard billed input (398.3M tokens), obscuring the 7.55B cache read tokens that were actually processed. 
*   **Action:** Update the frontend and statistics templates to display:
    $$\text{Total Context Input} = \text{input\_tokens} + \text{cache\_read\_input\_tokens}$$
    This correctly represents the context scale evaluated by Gemini.

### Recommendation 2: Retain the Subtraction Model
The subtraction model in `aggregateUsage` is correct. Unlike Anthropic where `input_tokens` is already non-cached, Gemini's protobuf maps total prompt size under the gateway's `inputTokens` conversion. Subtracting `cache_read_input_tokens` yields the correct billed token counts.
