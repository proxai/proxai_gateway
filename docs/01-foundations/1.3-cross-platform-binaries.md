# 1.3 Cross-Platform Binaries

*Last Updated: 2026-05-27*

> Which targets the gateway builds for, what `bun build --compile` does, and how each install vector picks the matching binary.

The gateway compiles to six per-platform native binaries — one for each `(OS, CPU architecture)` pair the team supports. Bun's `--compile` flag (which bundles the entire app plus a copy of the Bun runtime into one self-contained native executable) makes cross-compilation a first-class feature, so all six can be produced from a single Linux runner.

| Target | Bun flag | Output |
| --- | --- | --- |
| `darwin-arm64` | `bun-darwin-arm64` | `dist/darwin-arm64/proxai-gateway` |
| `darwin-x64` | `bun-darwin-x64` | `dist/darwin-x64/proxai-gateway` |
| `linux-arm64` | `bun-linux-arm64` | `dist/linux-arm64/proxai-gateway` |
| `linux-x64` | `bun-linux-x64` | `dist/linux-x64/proxai-gateway` |
| `windows-x64` | `bun-windows-x64` | `dist/windows-x64/proxai-gateway.exe` |
| `windows-arm64` | `bun-windows-arm64` | `dist/windows-arm64/proxai-gateway.exe` |

The list lives in `scripts/build.ts`:

```ts
const TARGETS: readonly Target[] = [
  { platform: 'darwin', arch: 'arm64' },
  { platform: 'darwin', arch: 'x64' },
  { platform: 'linux', arch: 'arm64' },
  { platform: 'linux', arch: 'x64' },
  { platform: 'windows', arch: 'x64' },
  { platform: 'windows', arch: 'arm64' },
];
```

There is one quirk on the macOS x64 line: prebuilt darwin-x64 binaries are **not** distributed via the curl-bash installer. `install.sh` rejects the Intel-Mac case with a hard error and tells the user to build from source. The build target still exists for development.

## What `bun build --compile` does

`bun build --compile --target=<flag> --outfile=<path> src/main.ts` is the build invocation. The flag does three things:

1. **Bundle.** It walks every import from `src/main.ts` and rolls the entire dependency graph into a single JavaScript bundle. Production dependencies under `node_modules/` are embedded into the output; no `node_modules/` directory ships.
2. **Transpile.** TypeScript is stripped to plain JS as part of the same pass (the typecheck has already happened separately via `tsc --noEmit`).
3. **Static-link Bun.** A copy of the Bun runtime is statically linked into the output. The result is a native executable that does not require Bun (or Node) installed on the host — the runtime is inside the binary.

The shipped artifact is a single file. On POSIX targets that is `proxai-gateway` (no extension); on Windows it is `proxai-gateway.exe`. The output naming is hard-coded in `outfileFor()` in `scripts/build.ts`.

## Binary sizes

Approximate sizes from a local build (these vary with Bun's runtime size per release):

| Target | Size |
| --- | --- |
| darwin-arm64 | ~62 MB |
| darwin-x64 | ~68 MB |
| linux-arm64 | ~91 MB |
| linux-x64 | ~92 MB |
| windows-x64 | ~96 MB |
| windows-arm64 | ~92 MB |

Linux and Windows binaries are larger than macOS because the statically-linked Bun runtime carries more platform glue on those targets. None of these are stripped — `bun build --compile` does not currently expose a strip flag.

## How the build script is invoked

`bun scripts/build.ts <target>` builds one target. `bun scripts/build.ts` with no argument builds all six in series. The script accepts only the six target names from the `TARGETS` list; unknown values exit with `process.exit(2)` and a list of valid targets.

`package.json` exposes a per-target alias under `scripts.build:<target>` for each entry:

```json
"build:darwin-arm64": "bun scripts/build.ts darwin-arm64",
"build:darwin-x64":   "bun scripts/build.ts darwin-x64",
"build:linux-arm64":  "bun scripts/build.ts linux-arm64",
"build:linux-x64":    "bun scripts/build.ts linux-x64",
"build:windows-x64":  "bun scripts/build.ts windows-x64",
"build:windows-arm64":"bun scripts/build.ts windows-arm64",
```

`package.json`'s `scripts.validate` is the most aggressive local gate; it ends in `bun run build:darwin-arm64` so a developer on Apple Silicon proves the binary compiles on every validate.

The CI release workflow uses these named scripts. `.github/workflows/release.yml` defines a matrix over five of the targets (excluding `darwin-x64`) and runs `bun run build:${{ matrix.target }}`. To verify the ad-hoc signature on macOS, the `darwin-arm64` target runs on a `macos-latest` runner, while the other four targets (`linux-arm64`, `linux-x64`, `windows-x64`, `windows-arm64`) run on `ubuntu-latest`. While cross-compilation is a first-class feature of `bun build --compile` (enabling a Linux host to build both Windows and Linux binaries), the macOS signer requires a macOS host.

## How each install vector picks the binary

### curl-bash on macOS / Linux (`install.sh`)

`install.sh` uses `uname -s` and `uname -m` to detect the host:

```sh
detect_os() {
  case "$(uname -s)" in
    Darwin) echo "darwin" ;;
    Linux)  echo "linux" ;;
    *) err "unsupported operating system" ;;
  esac
}

detect_arch() {
  case "$(uname -m)" in
    arm64|aarch64) echo "arm64" ;;
    x86_64|amd64)  echo "x64" ;;
    *) err "unsupported architecture" ;;
  esac
}
```

The matched `${os}` and `${arch}` go into the download URL:

```
https://github.com/proxai/proxai_gateway/releases/${path}/proxai-gateway-${os}-${arch}
```

`${path}` is either `latest/download` (default) or `download/${PROXAI_GATEWAY_VERSION}` (when the env var is set). The script downloads to `${HOME}/.proxai/bin/proxai-gateway`, chmods `+x`, and atomically moves into place.

Intel-Mac (darwin-x64) is rejected with a hard error suggesting `bun run build:darwin-x64` from source. Apple Silicon (arm64) Macs only for the prebuilt path.

### PowerShell on Windows (`install.ps1`)

`install.ps1` detects architecture via `$env:PROCESSOR_ARCHITECTURE`:

```ps1
function Get-ProxaiArch {
    if ($env:PROCESSOR_ARCHITECTURE -eq 'ARM64') { return 'arm64' }
    if ([Environment]::Is64BitOperatingSystem) { return 'x64' }
    throw "unsupported architecture"
}
```

The download URL uses the `win32` platform string (the npm/release naming convention) plus the matched arch:

```
https://github.com/proxai/proxai_gateway/releases/${path}/proxai-gateway-win32-${arch}.exe
```

The binary lands at `$env:USERPROFILE\.proxai\bin\proxai-gateway.exe`. The script adds the install dir to the user-level `PATH` environment variable.

### npm-family postinstall (`@proxai/gateway` package)

`npm install -g @proxai/gateway` (or pnpm/yarn/bun equivalents) installs a small published package whose `postinstall` hook (a script npm runs automatically after install) downloads the matching binary. `npm/postinstall.js` runs in Node and detects the platform via `process.platform` + `process.arch`:

```js
const platform = process.platform;  // 'darwin' | 'linux' | 'win32'
const arch = process.arch;          // 'x64' | 'arm64'
const ext = platform === 'win32' ? '.exe' : '';
const url = `https://github.com/proxai/proxai_gateway/releases/download/v${version}/proxai-gateway-${platform}-${arch}${ext}`;
```

The download lands in the package's `bin/proxai-gateway[.exe]`. The shim `npm/shim.js` is what npm wires up as the `proxai-gateway` executable; it `spawnSync`s the downloaded native binary on every invocation and exits with its exit code.

The release workflow renames the asset for npm consumption: `windows-*` artifacts are uploaded to the release as `proxai-gateway-win32-*.exe` to match Node's `process.platform = 'win32'`. The darwin and linux assets keep their platform string unchanged. The renaming is the `REMAP` table in `.github/workflows/release.yml`.

### Homebrew (`proxai/tap/proxai-gateway`, future)

Not yet shipped. A Homebrew tap is a third-party package repo for `brew`; the future formula will pin to a release tag, download the matching `darwin-arm64` or `darwin-x64` asset, and place the binary under `/usr/local/Cellar/` or `/opt/homebrew/Cellar/`. Because brew owns that path, the auto-upgrade flow in the daemon writes the `UPDATE_AVAILABLE` sentinel instead of replacing the binary in place — the operator runs `brew upgrade` themselves. The branching logic lives in the heartbeat cycle (see [install, upgrade, and uninstall](../07-platform-and-deployment/7.2-install-upgrade-uninstall.md)).

### Scoop (Windows, future)

Not yet shipped. Scoop is a Windows command-line installer; its manifests live in named "buckets" (repos). The future Scoop manifest will download the matching `windows-x64` or `windows-arm64` `.exe` and place it under `%USERPROFILE%\scoop\apps\proxai-gateway\`.

## Where the binary lands per install vector

| Install vector | Binary path |
| --- | --- |
| `install.sh` (macOS / Linux) | `~/.proxai/bin/proxai-gateway` |
| `install.ps1` (Windows) | `%USERPROFILE%\.proxai\bin\proxai-gateway.exe` |
| `npm` / `pnpm` / `yarn` / `bun` | `<global-prefix>/@proxai/gateway/bin/proxai-gateway[.exe]` (resolved via the shim) |
| `brew` (future) | `/usr/local/Cellar/proxai-gateway/<version>/bin/` or `/opt/homebrew/Cellar/...` |
| `scoop` (future) | `%USERPROFILE%\scoop\apps\proxai-gateway\current\proxai-gateway.exe` |

The path matters at upgrade time. The heartbeat cycle's `runAutoUpgrade` writes the new bytes to the running binary's location (everywhere except brew, and except Windows where it stages at `<path>.new` because Windows refuses to overwrite a running executable). See [install, upgrade and uninstall](../07-platform-and-deployment/7.2-install-upgrade-uninstall.md) for the full upgrade story.

These are the **binary** install locations, not where the gateway keeps its state. On POSIX both happen to live under `~/.proxai/`, so do not confuse the two: the executable lands in `~/.proxai/bin/`, while config, buffer, sentinels, and the control socket live in the profile-nested state tree at `~/.proxai/proxai-gateway/<profile>/` (one subtree per profile — `prod` and `dev`). A single installed binary serves both profiles; which profile a daemon runs as is selected by the `--profile` argument the service unit passes to the hidden `run` command. See [the overview's on-disk layout](./1.1-overview.md#where-does-state-live-on-disk) for the full per-platform state-directory table.

## Release asset naming on GitHub

The CI release workflow uploads five binary assets to each tagged release plus a checksum file. The on-disk file naming convention is `proxai-gateway-<platform>-<arch>[.exe]`, where `<platform>` follows the Node/npm convention (`win32` instead of `windows`) so the npm postinstall picks up the right asset directly:

```
proxai-gateway-darwin-arm64
proxai-gateway-linux-arm64
proxai-gateway-linux-x64
proxai-gateway-win32-arm64.exe
proxai-gateway-win32-x64.exe
checksums.txt
```

`darwin-x64` is **not** in the release assets — the curl-bash installer rejects that case, and the npm postinstall would hit a 404 on Intel Macs. That is intentional pending demand.

The mapping from the build-output directory name (`windows-x64`) to the release asset name (`win32-x64`) is the `REMAP` block in `.github/workflows/release.yml`:

```sh
declare -A REMAP=(
  [darwin-arm64]=darwin-arm64
  [linux-arm64]=linux-arm64
  [linux-x64]=linux-x64
  [windows-x64]=win32-x64
  [windows-arm64]=win32-arm64
)
```

The checksums file is generated with `sha256sum` over the renamed files inside `release/`. Every install vector that downloads from the GitHub release can verify the binary against `checksums.txt`.

## Why six build targets but only five release assets

The release matrix omits the macOS x64 build because Apple Silicon has been the Mac default since late 2020; Intel-Mac users get a clear error message from `install.sh` rather than a silent fallback. The build target is kept available for developers who explicitly need to produce that binary (the `scripts.validate` step uses `darwin-arm64`, not `darwin-x64`).

The Windows ARM64 build is shipped despite ARM Windows being rare because CI runs the full test suite on a `windows-11-arm` runner, and once the test matrix already covers it, shipping the binary is free.
