# 1.2 Tech Stack

*Last Updated: 2026-06-16*

> The runtime, language, and dependency surface the gateway is built on, and why each choice is there.

The gateway runs on [Bun](https://bun.com) — the JavaScript/TypeScript runtime the gateway is built on; provides native SQLite, zstd, fast install, and `--compile` for single-binary output. `package.json` declares `"engines": { "bun": ">=1.3.0" }`; CI pins `bun-version: 1.3.14` in every workflow. Bun is both the development toolchain (test runner, package manager, TypeScript loader) and the runtime that gets baked into the shipped binary via `bun build --compile` — Bun's flag that bundles the entire app plus a copy of the Bun runtime into one self-contained native executable.

The choice of Bun is load-bearing for three concrete capabilities the gateway depends on:

1. **Single-binary distribution.** `bun build --compile --target=bun-<platform>-<arch>` produces a self-contained native executable with the Bun runtime statically linked in. The user installs one file. No `node_modules/`, no `node` on PATH, no shebang resolution.
2. **Built-in SQLite.** `bun:sqlite` ships as part of the runtime — no `better-sqlite3` native-module compilation, no Prebuilt binary download dance. The local buffer (`buffer.db`) opens through `import { Database } from 'bun:sqlite'`.
3. **Built-in zstd.** `Bun.zstdCompressSync` is in the standard library (zstd is Zstandard, a fast compression algorithm with a tunable level; the gateway uses level 3 as the default). The batching pipeline calls it directly. No `node-zstd` C++ build step.

Bun also gives the project a fast test runner (`bun test`), a fast install (`bun install --frozen-lockfile`), and a TypeScript loader that runs `.ts` files without a separate transpile step — which is how `bun scripts/build.ts` works.

## Language: TypeScript

Strict TypeScript end to end. The `tsconfig.json` settings are deliberately aggressive — every option that catches a class of bugs at compile time is on:

- `strict: true` — full strict family.
- `noUncheckedIndexedAccess: true` — array/record indexing returns `T | undefined`.
- `exactOptionalPropertyTypes: true` — `undefined` is not silently assignable to optional fields.
- `noImplicitOverride`, `noFallthroughCasesInSwitch`, `noUnusedLocals`, `noUnusedParameters`.
- `verbatimModuleSyntax: true` — type-only imports must use `import type`.
- `allowImportingTsExtensions: true` — imports include the `.ts` suffix everywhere; this is consistent with Bun's loader and avoids the Node-vs-bundler import path drift.

The `paths` block under `compilerOptions` gives every directory under `src/` a bare-name prefix (`cli/*`, `core/*`, `services/*`, `sources/*`, `scripts/*`) so imports never have to traverse `../../../`.

The runtime target is `noEmit: true` — TypeScript exists only to typecheck. Bun runs the `.ts` source files directly.

## Production dependencies

The `dependencies` block in `package.json` is intentionally small. Every entry below ships inside the compiled binary, so each one was chosen with the binary size and security surface in mind.

| Dependency | Used for |
| --- | --- |
| `@inquirer/prompts` | Interactive prompts during `setup`, `uninstall`, and the release CLI. Replaces the older `inquirer` package with smaller per-prompt entry points. |
| `chalk` | Coloured terminal output across the CLI (status sections, log levels, prompts). |
| `commander` | The CLI framework that defines subcommands and option parsing. `main.ts` wires every subcommand through commander. |
| `ora` | Spinner UX during downloads (`upgrade`, the npm postinstall shim). |
| `pino` | pino is a structured-JSON logger — used for both the daemon's log file and the CLI's `--json` payloads. |
| `pino-pretty` | Pretty-prints pino lines for `tail` when stdout is a TTY. |
| `pino-roll` | pino-roll layers daily and size-based file rotation on top of pino for the daemon's log file (kept under `Logs/`). |
| `smol-toml` | smol-toml is a small TOML parser; the config file is TOML. Smaller and stricter than the more popular `@iarna/toml`. |
| `uuid` | Generates the synthetic `host_id` salt when no platform UUID is available, and the per-batch idempotency keys the uploader carries. |
| `xstate` | Powers the state-machine-driven daemon actors and coordination loops (such as rate-limit pacing and binary freshness checks). |

That is the complete production dependency list. There is no HTTP framework — the gateway is a client, not a server, and uses Bun's built-in `fetch`. There is no ORM — `bun:sqlite` is used directly with prepared statements (a prepared statement is a parsed-and-cached SQL statement executed many times with different parameter values, faster than re-parsing the SQL each call). There is no validation library — the config validator is hand-rolled to keep the binary small.

## Bun APIs used directly

Several Bun-namespace APIs are used in place of equivalent npm packages, which is part of how the binary stays small:

- `import { Database, constants } from 'bun:sqlite'` — opens `buffer.db` and the source databases (cursor's `state.vscdb`, codex's `state_*.sqlite`, gemini's `*.db` Cascade trajectory databases). The `constants` export carries the bitmask flags needed for the read-only / URI-aware open (see Pattern 3 in the cross-platform test notes).
- `Bun.zstdCompressSync(input, { level: 3 })` — compresses each batch body before insertion. Level 3 is the default compression level — chosen because it's the sweet spot of zstd's speed-vs-ratio curve for short live data, where archival-style ratios aren't worth the CPU. The default level parameter `3` is defined in `core/utils/compress.ts`.
- `Bun.file(path)` / `Bun.write(path, value)` — file I/O across writers (config, service-unit XML/plist/unit-file, npm-build staging).
- `Bun.spawn({ cmd, ... })` — every external process call: `launchctl`, `systemctl`, `schtasks`, `tasklist`, the package-manager sweep during uninstall, and the `bun build --compile` invocations inside `scripts/build.ts`.
- `Bun.which(name)` — resolves a command name to a full path before any spawn (canonical pattern from `services/uninstall/sweep.ts`; see Pattern 15 in the cross-platform test notes).
- `Bun.gc(true)` — explicitly invoked by the cross-platform `rmRecursive` helper after closing sqlite databases on Windows so the OS file handle is released before the directory is unlinked (Pattern 2).

## Dev tooling

The dev surface stays close to what Bun ships and a handful of well-supported sidecar tools.

| Tool | Role |
| --- | --- |
| `oxlint` | A fast Rust-based ESLint-compatible linter the gateway uses for code health checks. Configured in `.oxlintrc.json` with the `correctness` category set to `error`, `suspicious` and `perf` to `warn`, and `style` disabled (formatting is Prettier's job). Selective per-file overrides relax `no-await-in-loop` inside the polling and uploader loops where sequential awaits are deliberate. |
| `prettier` | Formatter. `prettier.config.mjs` defines the project style: single quotes, trailing commas, 100-char print width, LF endings. `bun run format:check` is the CI gate. |
| `husky` + `lint-staged` | husky installs git hooks; lint-staged runs configured commands against staged files only. `.husky/pre-commit` runs `bunx lint-staged` (Prettier on staged TS/JS/JSON/MD/YAML) and then `bun run lint`. The hook is installed by `prepare: "husky || true"` after `bun install`. |
| `typescript` | The compiler runs in typecheck-only mode (`tsc --noEmit`). The runtime never invokes it. |
| `@types/bun` | Type definitions for the Bun namespace and `bun:sqlite`. |
| `@statelyai/inspect` | The Stately browser visualizer for xstate machines. Loaded only via a dynamic `import('@statelyai/inspect')` in the daemon-actors layer when the developer-only `xstate` command starts the daemon with inspection enabled; it never loads in a normal run. |

The test runner is Bun's built-in `bun test`. Two scripts cover the lifecycle: `bun test --parallel --timeout 30000` for the day-to-day pipeline (`scripts.test`) and a coverage runner (`scripts.test:cov`) that runs `bun scripts/coverage-flow/index.ts`. The coverage runner executes tests serially with automatic retries for flaky failures and handles coverage report finalization to avoid deadlocks. The coverage threshold is configured in `bunfig.toml`: `coverageThreshold = { line = 1.0, function = 1.0 }` — 100% line and function coverage are CI-enforced (`coverageSkipTestFiles = true` keeps the test files themselves out of the denominator).

## Why no Node runtime ships

The gateway is distributed as a compiled single binary. Users running `proxai-gateway` are running the bun-compiled native executable; Bun's runtime is statically linked in. No Node, no npm, no global `node_modules/` is involved at runtime.

The one Node-shaped surface that exists is the npm install vector: when a user runs `npm install -g @proxai/gateway`, npm runs `npm/postinstall.js` (Node-based) — a postinstall hook is a script npm executes automatically after a package is installed. The hook detects the platform via `process.platform` + `process.arch` and downloads the matching native binary from the GitHub release into the package's `bin/` directory. The shim (`npm/shim.js`) then `spawnSync`s the binary on every invocation. The npm package itself is a thin downloader — the actual gateway is still the native binary, identical to the curl-bash install's payload.

[See cross-platform binaries](./1.3-cross-platform-binaries.md) for the build targets, output paths, and per-install-vector binary placement.

## What the test runner does

`bun test --parallel` walks every `*.test.ts` under `src/` and `scripts/` (the `include` block in `tsconfig.json` covers both roots). Per-file test execution is parallelised across worker threads. Each test file is isolated only at the module-mock level when discipline is followed (see Pattern 8 of the cross-platform test notes — `mock.module` is process-global, not file-scoped).

The coverage runner (`bun scripts/coverage-flow/index.ts`) runs `bun test --coverage` against the same tree, retries coverage gaps, and emits coverage that has to clear the `bunfig.toml` thresholds. It is the gate for the CI's `Code Quality` job.

## What it does not depend on

Several common dependencies are deliberately absent — knowing what is *not* in the stack is part of the mental model:

- **No bundler.** Bun loads `.ts` directly. `bun build --compile` is the only build step.
- **No web framework.** The gateway is a client; the only HTTP it does is outbound `fetch` to the ProxAI ingest backend.
- **No native modules.** No `better-sqlite3`, no `node-gyp`, no platform-specific prebuilds. Everything that would need native code (sqlite, zstd, hashing) is in the Bun standard library.
- **No build orchestrator.** No webpack, no esbuild config, no turbo. `scripts/build.ts` is one TypeScript file; it shells out to `bun build --compile` six times, once per target.

The runtime closure is small enough that the compiled binary is on the order of tens of megabytes per platform.
